# ADR-003. Выбор технологии для потоковой обработки событий.

**Дата:** 2026-06-04

**Статус:** Accepted

## Контекст
Показы рекламы создают большой поток данных для записи, а так же высокую нагрузку при аналитике.

Рассматривались три альтернативы:
1. Прямая запись в релиационную БД PostgresSQL
2. Запись в аналитическую БД через буфером

### Альтернатива 1: Прямая запись
Плюсы: минимальные изменения, быстрый time-to-market, только смена быза в которую пишем.
Минусы: Высокая нагрузка на запись в БД проблема с времинем обработки аналитических запросов, возможная потеря данных при высокой нагрузке, сбой сервисов сбора статистики.

### Альтернатива 2: Запись в аналитическую БД через буфером
Плюсы: Буфер в виде Kafka хоршо маштабируется по как записи так и по чтению, возможна настройка разных уровней подтверждения записи имеет прямую интеграцию со множеством аналитических баз данных.
Возможность перечитывания данных при выявлении проблем.
Использование Clickhouse в качестве аналитической БД позволяет ускорить обработку аналитических запросов в несколько раз по сравнение с PostgreSQL.
Минусы: Переписывания как сервисов сбора статистики так и аналитической обработки. Развертывание дополнительных компонентов. 

## Решение

- Развертываем кластер kafka и Clickhouse
- Взаимодействие модуля statsService осуществляем через топики kafka

## Последствия

**Положительные:**
- Снижение нагрузки с оперативных БД
- Повышение скорости аналитики
- Наличие буфера сообщений на случай сбоев, с возможностью перечитать заново. 
- Возможность маштабирования буфера из коробки при резком увеличение нагрузки

**Отрицательные:**
- Появление новых систем требуется обучение разработчиков
- Новые системы на сопровождении DevOps

**Риски:**
- Если пиковая нагрузка превысит 50K RPS, потребуется выделение модуля
  в микросервис. Оценка разработки — 2–3 недели при наличии чётких интерфейсов
- Конкуренция за пул подключений к PostgreSQL при одновременном пике
  бронирования и аналитических запросов
